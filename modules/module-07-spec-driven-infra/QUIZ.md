# M07 Quiz: Spec-Driven Infrastructure

9 questions. Pick one answer, then open the reveal to check it and read why.

---

**1. What does a written spec have that a one-line intent doesn't?**

- A. Better grammar
- B. Requirements, constraints, and acceptance criteria, stated before generation
- C. A longer file
- D. A guarantee that checkov passes clean

<details>
<summary>Answer</summary>

**B.** A one-line intent has a goal and nothing else. A spec adds three specific,
checkable parts: what the thing must do, what it must never do, and how you'll verify it,
all written down before any code exists. Length (C) and grammar (A) aren't the point. A
spec never guarantees a fully clean scanner run (D), it only covers what its author wrote
down.

</details>

---

**2. A ticket says "give me an autoscaling web tier for our checkout service." Generated with no
spec, iterated on by feel until it looks done. What is this?**

- A. Spec-driven development
- B. Vibe coding
- C. A gate
- D. Policy as code

<details>
<summary>Answer</summary>

**B, vibe coding.** Generate, eyeball, tweak, eyeball again, with no written target and no
fixed acceptance criteria. This course names it once, as a failed approach on
infrastructure specifically, not as a technique to weigh against spec-driven work.

</details>

---

**3. Why does vibe coding fail on infrastructure specifically, more than it fails on
application code?**

- A. Infrastructure code is harder to read
- B. Terraform has stricter syntax than most languages
- C. No undo, and failure that stays quiet until someone looks, the same asymmetries from M01
- D. Infrastructure teams don't use version control

<details>
<summary>Answer</summary>

**C.** An autoscaling tier generated by feel, with a health check grace period too short for a
real cold boot and a scale-in policy that can kill the newest release, applies cleanly, same as a
careful one. Application code that's "close enough" usually gets fixed in the next release.
Infrastructure that's "close enough" is often already live, already serving real traffic, before
anyone reads it carefully. That's M01's no-undo and silent-failure properties, not a syntax
complaint (B) or a tooling complaint (D).

</details>

---

**4. A spec's success criteria pin down five things: grace period, scale-in policy, capacity
bounds, cooldown, and IMDSv2. Checkov still finds a real failure on the generated module: missing
tags on the launch configuration, something the spec never mentioned. What does this mean?**

- A. The spec was written badly and should be rejected
- B. Checkov is buggy
- C. The spec did its job, it just didn't cover everything checkov checks, which is exactly why the policy gate in M09 still runs afterward
- D. The module should be regenerated until checkov passes fully clean

<details>
<summary>Answer</summary>

**C.** A spec's acceptance criteria only cover what its author thought to write down. That
gap isn't a flaw in spec-driven work, it's the whole reason M09's policy check exists as a
separate stage. Regenerating until checkov is fully clean (D) treats the spec as if it
should replace the scanner, which was never the plan.

</details>

**5. Given the course thesis "the agent proposes, the pipeline decides," where does a spec
fit?**

- A. It replaces the gate in M06, since a good spec means apply is already safe
- B. It defines the ask, before generation happens at all, it doesn't block or scan anything itself
- C. It's the same thing as a policy check, just written earlier
- D. It only matters for Tier 0 exercises

<details>
<summary>Answer</summary>

**B.** A spec is nothing but a better question, asked before generation starts. The gate
(M06) blocks apply based on something mechanical. The policy check (M09) scans the plan
against rules neither you nor the spec's author necessarily thought of. Three different
jobs, three different moments, and `apply` still needs a gate whether the module came from
a careful spec or ten seconds of guessing (ruling out A and C). Real reviewers and real
consequences apply well beyond Tier 0 (D).

</details>

**6. A team lead says: "We don't need specs, we have checkov in CI." What's the gap in
that argument?**

- A. Checkov is slower than writing a spec
- B. Checkov catches what's in its ruleset after generation, it can't determine what gets generated in the first place, and it won't catch an org-specific rule nobody encoded
- C. Specs and checkov do the exact same job
- D. Checkov only works on Terraform, not other languages

<details>
<summary>Answer</summary>

**B.** Checkov runs after the fact, against its own ruleset. It has nothing to say about a
requirement that's specific to your team (a naming convention, which artifacts get which
retention) unless someone encodes it as a policy. A spec defines the ask before generation;
checkov checks the result afterward. Different jobs (ruling out C), and the gap isn't about
speed (A) or language support (D).

</details>

**7. A throwaway Tier 0 exercise, nobody will review it, nothing depends on it. Do you
need a written spec?**

- A. Yes, always write a spec, no exceptions
- B. No, a one-line intent is enough here, the overhead is only worth it once a real reviewer or a real consequence enters the picture
- C. No, specs are only for Tier 2 and Tier 3 labs
- D. Yes, but only if the exercise uses Terraform

<details>
<summary>Answer</summary>

**B.** A spec costs real time to write. That cost is worth paying once someone else will
review the result, or it holds real data, or runs in a real account. A throwaway exercise
nobody else will ever look at doesn't clear that bar. This isn't a lab-tier rule (C) or a
tool-specific rule (D), it's about reviewers and consequences.

</details>

**8. This lab's vibe-coded run and spec-driven run both start from the same seven-word
ticket. The vibe-coded run also builds a load balancer, two security groups, and a target
group, none of which the spec required. What does that show?**

- A. The vibe-coded run is more thorough, so it's actually the better answer
- B. A spec doesn't just pin down ambiguous numbers, it bounds scope too, an unscoped ask lets the agent invent surface area nobody asked it to build or secure
- C. This never actually happens in practice, it's a hypothetical
- D. Checkov would have caught this anyway so it doesn't matter

<details>
<summary>Answer</summary>

**B.** The vibe-coded run's extra load balancer looked reasonable in isolation and added nine
real checkov findings (no deletion protection, no access logging, no WAF, HTTP instead of
HTTPS) on infrastructure nobody's requirement ever named. More surface area isn't more
thorough (A), it's more unreviewed risk. This is the real, captured output from this
module's own lab, not a hypothetical (C), and checkov catching it later (D) is exactly why
it matters that it was never scoped in the first place, not a reason to shrug it off.

</details>

**9. Both modules answer the same ticket. The vibe-coded run sets `health_check_grace_period
= 60` and leaves `termination_policies` unset. The spec-driven run sets `180` and an
explicit ordered list. Which module is "wrong"?**

- A. The vibe-coded one, it's invalid Terraform
- B. Neither is invalid HCL, both apply cleanly, the difference is that one made five real judgment calls silently and the other made them on purpose and wrote them down
- C. The spec-driven one, it's needlessly verbose
- D. There's no real difference, both are the same underlying infrastructure

<details>
<summary>Answer</summary>

**B.** `terraform apply` doesn't know or care whether a value was reasoned about or guessed.
Both modules are valid, both apply. The difference only shows up later: a `60`-second grace
period is real risk on a cold `dnf install` boot, and an unset termination policy means AWS's
own default decides which instance dies first, not a decision this team actually made. Neither
"invalid" (A) nor "same infrastructure" (D) is true, and writing the reasoning down isn't verbosity
(C), it's the whole point of a spec.

</details>
